=== WHAT I FOUND IN THE CODE (verify each of these; correct me where I'm wrong) ===
1. THERE IS NO PULL LOOP TODAY. db/jobs.py::claim_next_job exists and is atomic, but grep
   shows it is called ONLY from harness/tests/test_jobs.py and harness/scripts/smoke_dispatch.py.
   The live path is PUSH, IN-PROCESS: dispatch.py::dispatch_local (line ~181-184) sets status
   'in_progress' and then calls executor.start_in_background(job_id) — a thread in the same
   process as the record. So the architecture doc's claim "workers ask the record for work;
   moving workers to other machines is plumbing on a design that already assumes it" looks
   false to me. Also claim_next_job filters on status='todo', which dispatch_local never
   leaves a job in.
2. claim_next_job claims BY builder_seat, has NO worker identity, NO lease, NO expiry, NO
   heartbeat. jobs has no worker column. 'stalled' is not in the jobs.status CHECK constraint
   (schema.sql ~279). attempts increments per claim with no ceiling.
3. THE PANEL AND ALL RECORDING ARE IN-PROCESS TODAY. executor.run_job calls
   gauntlet.run_panel; each reviewer thread opens its OWN sqlite connection (gauntlet.py
   _review_one) and calls db.jobs.record_verdict / record_artifact / set_status directly.
   The schema triggers verify a verdict's tier/family against the seats table but CANNOT
   verify that a review actually happened. artifacts.captured_by ('harness'|'playwright'|
   'model') is enforced by a trigger that only reads the value in the row — trust today comes
   from the writer being in-process, not from anything checkable.
4. SPEND: gauntlet._reserve_review_budget imports gatekeeper and calls gatekeeper.spend
   in-process on the panel's own writable connection. Caps are DB triggers on INSERT INTO
   usage (guard_daily_cap_is_hard / build / review / monthly).
5. GATEKEEPER: gatekeeper.serve() is LOOPBACK-ONLY by explicit design ("the tailnet is other
   devices, and the whole point of this process is that reaching it is harder than reaching
   the agents") + a shared token in ~/.chief/gatekeeper.token. gatekeeper.merge does REAL GIT
   WORK in a repo on the machine it runs on: _branch_tip, _diff_bundle, _commit_holds_the_
   reviewed_work, _repo_is_ready, _git_merge, and it compares the branch tip against
   jobs.head_version and the committed diff against jobs.result byte-for-byte.
6. Nothing ever pushes job/<id> anywhere (queue task 12 says so). So if the builder runs on a
   worker, the home has no git objects to verify or merge.
7. DISPATCH STAMPS THE PANEL SIZE FROM LOCAL PROBING: dispatch.panel_roster ->
   gauntlet.has_runner probes THIS MACHINE (is `claude` logged in, is `codex` logged in, is
   XAI_API_KEY set) and writes required_reviews / required_review_families onto the job
   (un-lowerable by trigger). On the home, none of those CLIs may exist.
8. VOICE: server.py::voice_token mints an OpenAI ephemeral client secret from OPENAI_API_KEY
   loaded from ~/.chief/env by _load_chief_env; the browser then talks DIRECTLY to the vendor.
   The mouth's only tool posts to /api/voice/ask (+ /api/voice/ask/stream, SSE) on the server.
   server.py binds 127.0.0.1:8787 and is exposed by `tailscale serve`. There is no auth on
   these endpoints other than being on the tailnet. A single held chief_live session
   (_chief_session) is process-global.
9. seats.toml is one file; seats are synced into the DB at server start (dispatch.sync_seats)
   from whatever machine runs the server. Metered seat = grok/xai with daily/build/review caps.
