BACKGROUND — READ THIS FIRST
============================================================
`harness/server.py::voice_ask` (POST /api/voice/ask) already uses the streaming
`ChiefSession` from `harness/chief_live.py`. `ChiefSession.say(said, deep=...)` is an
async generator that yields whole SENTENCES as Chief's answer streams in from the model.
Right now `voice_ask` collects every yielded sentence into a list and only returns once
the WHOLE answer is done — so the phone hears nothing until Chief has finished thinking.
That defeats the entire point of streaming. Your job is to add a second endpoint that
streams sentences out to the browser as they arrive, and to update the voice page
(`harness/web/voice.html`) to speak the first sentence almost immediately and queue the
rest instead of waiting for everything.

- harness/server.py — read lines ~600-690 (the `_chief_lock`, `_live_session()`,
  `voice_ask`, `_CHIEF_MODEL` import) plus the top of the file for `db()`, `app`, imports.

TASK 1 — new streaming endpoint: harness/server.py
============================================================
Add `POST /api/voice/ask/stream` immediately after the existing `voice_ask` function
(do not modify `voice_ask` itself — it must keep working byte-for-byte as it does today,
the text-first fallback depends on it). It returns a Server-Sent Events stream
(`text/event-stream`, via FastAPI's `StreamingResponse` — import it from
`fastapi.responses` alongside the existing imports).

Behaviour, mirroring `voice_ask` as closely as possible so nothing about recording or
recovery changes:

1. Parse `said` from the JSON body exactly like `voice_ask` does. If empty, stream a
   single `done` event: `{"full": "", "spoken": "I didn't catch that.", "model":
   _CHIEF_MODEL, "failed": true}` and stop (no `events` row for this case, matching
   today's behaviour where an empty `said` short-circuits before any Chief call).

2. Compute `pushed_back = is_pushback(said)` exactly like `voice_ask` (same import from
   `mouth`).

3. If `os.environ.get("OPENAI_API_KEY")` is set (the live streaming path):
   - Acquire `_chief_lock` exactly like `voice_ask` does (`async with _chief_lock:`),
     get the session via `_live_session()`, and iterate `session.say(said,
     deep=pushed_back)`.
   - For EACH sentence yielded, immediately emit an SSE event named `sentence` with
     JSON payload `{"text": <sentence cleaned through chief._for_speech>}`, and also
     keep collecting the raw (uncleaned) sentences into a list, exactly the way
     `voice_ask` collects `pieces`.
   - If the generator raises, catch it exactly like `voice_ask` does: drop the module
     global `_chief_session` (set it to `None` so the next turn rebuilds a clean
     session), and treat this turn as producing no answer — do NOT re-raise, do NOT let
     an unhandled exception surface as a raw error to the browser.
   - After the loop (success or the caught-exception case), build `answer = "
     ".join(pieces).strip()` (empty string if the exception path ran). If `answer` is
     non-empty: `out = {"spoken": _for_speech(answer), "full": answer, "model":
     _CHIEF_MODEL, "failed": False}` — same fields as `voice_ask`'s success branch,
     do NOT emit an extra `sentence` event for this case (every sentence was already
     streamed as it arrived).
   - If `answer` is empty (nothing yielded, or the exception path ran): `out =
     {"spoken": "Something went wrong on my end. Nothing's started.", "full": "Chief
     returned nothing. No work was dispatched.", "model": _CHIEF_MODEL, "failed": True}`
     — same text as `voice_ask`'s failure branch, word for word. In this case ALSO emit
     one `sentence` event carrying that same spoken failure text, so the mouth actually
     says something (in the success case sentences were already streamed, so no extra
     event is needed there).

4. If `OPENAI_API_KEY` is NOT set (the free fallback path): reuse the same fallback
   `voice_ask` uses — `talking_about = (body.get("context") or "").strip()`, `context =
   "\n\n".join(p for p in (_project_context(), talking_about) if p)`, `out =
   ask_chief(said, context=context, pushed_back=pushed_back)` — then emit ONE `sentence`
   event with `{"text": out["spoken"]}` before the `done` event (this path never streams
   incrementally; the existing subprocess-based `ask_chief` returns all at once).

5. Whichever path ran, write the SAME `events` INSERT that `voice_ask` writes today
   (same SQL, same params: `out.get("model", _CHIEF_MODEL)`, `out["full"][:500]`) —
   except for the empty-`said` short-circuit in step 1, which never reaches Chief at all
   and writes nothing, matching current behaviour (an empty `said` returns before
   `voice_ask` does its INSERT too — check this by reading `voice_ask` again: it returns
   `{"spoken": "I didn't catch that."}` before the `db()`/INSERT lines, so replicate
   that: no INSERT for empty `said`).

6. Finally emit one `done` SSE event carrying `out` (the full dict: `full`, `spoken`,
   `model`, `failed`).

Implementation notes:
   - Write a tiny local helper to format one SSE event, e.g.
     `def _sse(event: str, data: dict) -> str: return f"event: {event}\ndata:
     {json.dumps(data)}\n\n"` (module already imports `json`). Reuse it for every event
     you emit.
   - The endpoint function itself should be an `async def` that returns
     `StreamingResponse(_gen(), media_type="text/event-stream")` where `_gen` is an
     inner `async def` generator implementing steps 1-6. Keep the whole thing inside one
     function (nested generator is fine) so it reads top-to-bottom like `voice_ask` does.
   - Do not change `_CHIEF_MODEL`, `_chief_lock`, `_live_session`, or `voice_ask`.
   - Do not add response headers beyond `media_type` unless something in local testing
     shows FastAPI/Starlette needs them to stream — StreamingResponse over an async
     generator streams each yielded chunk as produced, no extra config should be needed.
